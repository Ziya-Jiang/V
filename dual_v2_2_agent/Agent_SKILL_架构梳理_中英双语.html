中文
新架构的本质不是“换了一个模型”。 它重新定义了模型、网页、Agent、Skill、Tool 与底层控制之间的权限边界。

传统 VLM + Functions 模式让模型选择并调用函数，规划和执行容易发生在同一链路中。 当前实现让模型或规则 Planner 只产生高层语义 Plan；Plan 本身不运动机器人， 必须经过白名单校验、现场检查和逐 Plan 批准，才会创建 Hardware Task。

Python Agent 是机械臂、相机与感知模型的唯一软件所有者。Skill 负责完整任务策略， Tool 负责原子能力，RobotRAM 继续承担已验证的感知、规划与执行。

最大收益：安全权威分离、任务可观测、能力可复用、故障可恢复。

主要代价：进程和状态更多、策略存在双份校验、Planner 泛化能力仍有限。

ENGLISH
The new architecture is not merely a model replacement. It reallocates authority across the model, UI, Agent, Skills, Tools, and control stack.

In a conventional VLM + Functions design, the model chooses functions and planning may flow directly into dispatch. The current implementation allows a rule-based or LLM Planner to propose only a high-level semantic Plan. A Plan is inert until allowlist validation, on-site checks, and per-Plan approval create a Hardware Task.

The Python Agent is the sole software owner of arms, cameras, and perception models. Skills own task strategy, Tools expose atomic capabilities, and RobotRAM continues to provide the validated perception, planning, and execution stack.

Primary gains: separated safety authority, observability, reuse, and recovery.

Main costs: more processes and state, duplicated policy checks, and limited planner generality.

Layered Architecture

层次结构 / System Layers

01操作入口 / InterfacesRobot Soul GUI + Harness：目标输入、Plan 审查、现场审批、Task Timeline。
02策略与审批 / PolicySkill 白名单、参数边界、动作预算、Plan TTL、checklist 与确认口令。

05Executor依赖校验、执行时语义解析、逐 Skill 执行与事件发送。
06Skill完整任务策略：感知、抓放、整理、恢复、启动。
07Tool3 个感知 Tool + 5 个操作 Tool，统一返回 ToolResult。

中文职责边界
  • Plan：纯数据，包含 instruction、SkillCall 与 constraints。
  • Skill：任务级组合，封装顺序、前置条件、失败恢复与业务语义。
  • Tool：确定性原子能力，是进入 RobotRAM 的受控适配层。
  • RobotContext：持有相机、机械臂、模型、标定和当前场景状态。
  • RobotRAM：底层能力被复用，而非被重新实现。
ENGLISH RESPONSIBILITIES
  • Plan: inert data containing instruction, SkillCalls, and constraints.
  • Skill: task-level composition owning order, preconditions, recovery, and semantics.
  • Tool: deterministic atomic capability and controlled adapter into RobotRAM.
  • RobotContext: owns arms, cameras, models, calibration, and current scene state.
  • RobotRAM: existing low-level capabilities are reused rather than rewritten.
关键不变量 / Key invariant 模型不能提交关节角、CAN、shell、任意坐标或任意原子调用；所有真机能力都通过 Plan → Approval → Task → Executor 漏斗收敛。The model cannot submit joint, CAN, shell, arbitrary pose, or arbitrary atomic calls; hardware authority narrows through one execution funnel.

中文

为什么执行时才解析物体？

Plan 使用 {"category":"cup","color":"blue"} 等语义引用。 感知完成后，Executor 才将其解析为 object_2。这样 Plan 不绑定某一次 检测的临时编号。

“整理桌面”怎样展开？

Planner 只提交一个 tidy_table Skill。Skill 内部感知场景、过滤缺失物体， 再对碗、面包和杯子逐项调用 pick_and_place。每项任务再由 Step4 生成详细动作序列。

错误怎样返回？

ToolResult → Skill → Executor → Server Task → 网页 Timeline。当前信息可以指出 “把什么放到哪里、在哪个动作、哪只手臂、目标位置及底层反馈”。

ENGLISH

Why resolve objects at execution time?

Plans carry semantic references such as {"category":"cup","color":"blue"}. After perception, the Executor resolves them to transient IDs such as object_2. The Plan therefore remains independent of one detection frame.

How does “tidy the table” expand?

The Planner emits one tidy_table Skill. The Skill perceives the scene, filters unavailable candidates, and invokes pick_and_place for the bowl, bread, and cup. Step4 then expands each placement into detailed motion actions.

How do errors propagate?

ToolResult → Skill → Executor → Server Task → Web Timeline. Current messages identify the object, target, failed phase, arm, target position, and low-level feedback.

Lifecycle & Supervision

launch_robot_soul.sh 改变了什么 / What the Launcher Adds

统一装配 / Unified assembly

预检、构建 Harness Web、准备配置、共享 token，并按顺序启动硬件面、Harness、GUI 与 Supervisor。

Preflight, web build, configuration, shared token, and ordered startup of hardware plane, Harness, GUI, and supervisor.

双模式 / Dual modes

start 直接启动真机栈；console 仅启动本地网页与 Harness，硬件保持 offline。

start boots hardware immediately; console keeps hardware offline until on-site startup.

显式状态机 / Lifecycle state

offline → starting → healthy / faulted → recovering

“网页在线”与“机器人可执行”成为两个独立状态。UI availability no longer implies hardware readiness.

故障域分离 / Fault isolation

Harness/GUI 连续失败触发完整安全停机；硬件面失败则锁定并停止硬件，但保留网页用于诊断和恢复。

Cognitive/UI failure stops the full stack; hardware failure locks the hardware plane while keeping diagnostics online.

现场恢复 / On-site recovery

网页启动和恢复都要求确认口令、生命周期互斥锁与 sudo 授权检查。

Web startup and recovery require confirmation, lifecycle locking, and valid sudo authorization.

统一退出 / Coordinated shutdown

Supervisor 与启动脚本统一清理 Agent、Planner、Upper 与 RT Control，减少残留进程和硬件所有权冲突。

Coordinated cleanup reduces stale processes and conflicting hardware ownership.

架构意义 / Architectural significance launch_robot_soul.sh 不只是 shell launcher，而是把认知面、操作面与硬件面装配为 一个具有健康检查、故障锁定和人工恢复能力的产品运行时。 It is a lifecycle supervisor and product assembly boundary, not merely a startup script.

Strengths & Constraints

优势与当前限制 / Strengths and Current Limits

优势 / STRENGTHS
安全权威分离模型提议、操作员批准、Agent 执行、控制栈驱动。
可观测Plan ID、Task、事件时间线和详细失败上下文。
可测试Planner、Skill、策略、审批、Origin 与状态机可以独立验证。
可复用pick_and_place 可被单任务与 tidy_table 共同组合。
渐进迁移保留 RobotRAM Step1–5 与控制栈，降低重构风险。
故障可恢复硬件故障不必杀死网页和 Harness。

English summary: authority separation, observability, independent testing, reusable Skills, incremental migration, and isolated recovery.

限制 / LIMITS
Planner 较窄主要覆盖整理桌面和单次抓放；开放任务泛化有限。
整理仍有配方按场景过滤候选，但尚未自动推导所有空间关系。
感知误检有效 mask/位姿仍可能对应错误语义，需要置信度与任务 allowlist。
场景可能过期移动物体后需要更新 world state 或重新感知。
状态主要在内存Agent 重启会丢失短期 Plan、审批与历史。
策略双份维护TS 与 Python 的白名单和动作预算可能漂移。
单 Task 串行安全但无队列、优先级和调度策略。
取消不是急停cancel_event 是协作式软件边界，不能替代实体急停。

English summary: narrow planning, recipe-driven tidying, semantic false positives, stale world state, in-memory lifecycle, policy drift, and no task queue.

需要直接指出的事实 / Important reality 当前架构已建立强执行边界，但还不是“通用自主机器人 Agent”。它更准确地说是一个 安全、可审查、可扩展的任务运行时，其 Planner 和世界模型仍处于早期阶段。 The execution boundary is strong, but the system is not yet a general autonomous robot; it is a safe and extensible task runtime with an early-stage planner and world model.

Roadmap

演进潜力 / Development Potential

短期 / SHORT TERM

先把运行时做稳 / Stabilize the runtime

  1. 使用单一 Skill Schema 生成 TS/Python 校验与动作预算。
  2. 每次放置后更新世界模型；被移动目标强制重新感知。
  3. 完整保留 operation、arm、action、pose 等结构化事件字段。
  4. 持久化 Plan、Task、审批、事件和执行结果。
  1. Generate TS/Python policy and budgets from one Skill Schema.
  2. Refresh or update world state after every placement.
  3. Preserve structured operation metadata end to end.
  4. Persist Plans, Tasks, approvals, events, and results.
中期 / MID TERM

让 Skill 真正可扩展 / Scale the Skill system

  1. 为 Skill 增加前置条件、后置条件、风险等级、版本与重试策略。
  2. 将整理任务升级为基于场景关系的动态 Skill DAG。
  3. 加入仿真回放、碰撞预检和 Plan Diff。
  4. 建立有限 Task 队列，同时保持硬件 Executor 串行。
  1. Add preconditions, postconditions, risk, versioning, and retries.
  2. Generate scene-driven Skill DAGs instead of fixed recipes.
  3. Add simulation replay, collision preflight, and Plan Diff.
  4. Queue Tasks while preserving one serial hardware Executor.
长期 / LONG TERM

释放 Agent 平台能力 / Unlock the platform

  1. 使用受 Skill Manifest 约束的 LLM Planner 支持开放目标。
  2. 多个只规划 Agent 并行提出方案，由单一执行 Agent 仲裁。
  3. 建立跨机器人 Capability Profile 与 Skill 版本兼容层。
  4. 利用执行结果与视觉复核形成闭环学习和主动恢复。
  1. Use manifest-constrained LLM planning for open-ended goals.
  2. Allow multiple planning agents but one execution authority.
  3. Build cross-robot capability profiles and version compatibility.
  4. Learn from execution outcomes and visual verification.

Conclusion & Source Map

结论与关键入口 / Conclusion and Source Map

必须保持的架构不变量
1

Python Agent 始终是唯一硬件所有者。

2

模型只能提交语义 Plan，不能直接提交关节、CAN、shell 或任意原子调用。

3

Plan 与 Task 始终分离；真机运动始终经过独立现场批准。

4

软件取消与 Supervisor 不能替代独立实体急停。

战略建议 下一阶段不应继续增加更多“模型可直接调用的函数”，而应增加带契约、版本、风险、 前后置条件和恢复策略的 Skill。
ARCHITECTURAL INVARIANTS
1

The Python Agent remains the sole hardware owner.

2

The model submits semantic Plans, never joints, CAN, shell, or arbitrary atomic calls.

3

Plan and Task remain separate; hardware motion always requires independent on-site approval.

4

Software cancellation and supervisors never replace the physical emergency stop.

Strategic recommendation The next phase should add contract-driven, versioned, risk-rated, recoverable Skills—not more functions directly exposed to the model.
