## 1. 任务目标与最终形成的问题分解

最初目标是在 `cart_book_grasp_v1_3` 基础上加入视觉伺服，提高书脊对准与前伸抓取的适应性。用户随后明确：书可能颜色不同、姿态倾斜、只露出部分书脊；不必把手移动到书的上下中心，主要要让腕部相机中央对准书脊中线，并允许绕工具轴旋转。

逐步形成的职责划分是：

1. **头部 RGB-D**：场景选书、基座 Y 粗对齐和目标 X 深度计算；可靠时估计书脊三维倾角。
2. **腕部 RGB**：近距离定位书脊，估计中线横向偏差和倾角，提供视觉外环误差。
3. **视觉外环**：控制 Y 与工具轴旋转；X 按本轮深度终点推进，Z 保持本轮参考平面。
4. **运动执行层**：普通动作使用 CuRobo；只有视觉阶段使用独立的 CPU 差分关节伺服。
5. **恢复与退出**：区分正常丢点、几何不一致、深度无效、反馈失效、执行故障。不同失败不能共用一个“放宽阈值继续”的策略。
6. **GPT**：在常规感知或中线几何无法可靠解释时提供图像区域提议；不直接输出关节命令，也不代替实测深度和反馈。

当前任务假设：**第一步 Y 粗对齐以后，腕部画面中央的书就是头部深度计算所对应的书。** 用户明确接受了这一假设，因而取消在线头腕身份匹配。该假设减少流程负担，但不能在论文里称作“已验证跨相机目标身份一致”。

## 2. 版本演进主线

### 2.1 V1.3：深度驱动的抓取基线

保留复位、头部感知、J7 姿态调整、Y 对齐、沿 X 分段前伸、合爪、抬升、停顿、下降、松爪、抽回、复位等动作。动作参数在各动作前热加载。

这一基线提供抓取顺序和深度终点；视觉伺服最初作为第二段前伸的改进加入，后来也承担 Y/旋转对准。

### 2.2 早期 V3：示教点和最终图像目标

先讨论“示教对准点 → Y/Z 图像闭环 → 原抓取”，再尝试用最终抓取示教图控制 XYZ 前伸。用户明确：保存的近景图是最终抓取示教图，机械臂之后已经退到第二段前伸前的观测位置。

关键困难是最终图与当前图的尺度差异、纹理不足，以及不同书无法复用同一本书的图像特征身份。

### 2.3 头腕特征匹配研究

比较 SIFT、XFeat、SuperPoint+LightGlue，以及 ROI、原始分辨率与低分辨率输入。高分辨率改善部分样本，但没有解决所有跨视角共同纹理不足的问题。

用户后来取消在线头腕匹配，改成粗对齐后的中心书假设。注意：取消身份匹配并不自动使原示教图适用于不同书，因此又改造了终点定义。

### 2.4 CoTracker + 距离终点

在本轮选中的书上初始化少量点，跟踪其图像中心，Y/Z 闭环；X 终点使用 V1.3 深度结果。不再要求匹配原书的最终纹理图。

该阶段暴露小步被规划器忽略、反馈到位不一致、采集超时、几何不一致、软件预算不足和计算开销等问题。

### 2.5 快速中线模式

用户明确不关心上下位置，改成中线横向对准，固定 Z；书倾斜时再加入绕工具轴旋转。曾尝试仅跟踪左右边界，后又恢复局部特征点传递中线。

当前特征跟踪是 **Shi–Tomasi + LK 光流 + RANSAC**，不是 CoTracker。点用于传递书脊中线，点的平均位置不应定义抓取中心。

### 2.6 V3.1：从停走路点到连续更新，再到直接伺服

最初目标是运动中更新视觉目标，建立独立规划器，不继续改旧规划器。随后经历轨迹重规划、接续、时间缩放、ACK、FK 并发和 UDP 类型问题。

用户进一步要求“只替换视觉伺服、不用 CuRobo 做这一段”。最终视觉阶段采用 CPU 差分伺服，普通动作仍使用 CuRobo。V3.1 文件名仍保留“planner”，不代表视觉阶段还调用 MotionGen。

### 2.7 V3.2：丢点后锁姿与有限时间恢复

统一丢点切换时的 Y、完整姿态及原始 Z 参考；区分短时偏差恢复与硬停止。位置到位容差调整为 3 mm，但运动高度边界、X 终点容差等没有同步无限放大。

同时优化腕部书脊选择，排除封面特征点，并加入头部 GPT 备用识别。

### 2.8 V3.3：头部最高原始分辨率

头部共享源提供当前设备支持的最高原始 RGB-D：本机记录为 Orbbec Gemini 305、1280×800、10 FPS。旧客户端仍可获取 848×530。内参、对齐深度与掩码必须使用同一坐标尺寸。

“最高”是该设备及 SDK 当时枚举的 profile，不是所有 Orbbec 型号的统一上限。

### 2.9 V3.4：边界连接研究，随后转向 GPT 区域恢复

先实现短边段连接、外边界拟合、文字线条排除、透视宽度检查与重复候选合并；之后用户要求 SAM3 被拒绝时直接用 GPT，而不是继续边界算法。

当前 V3.4 保留这些边界实验作为历史与离线研究。在线备用路径是 GPT 直接圈定书脊；最新又将 GPT 接到连续跟踪几何失败后的停稳恢复流程。

## 3. 相机标定、坐标系与工作空间可视化

### P01：标定板规格与内角点数

用户最初提供 12×9 标定板、格子边长 1 cm，希望用成熟工具快速标定。ROS `camera_calibration` 是实际讨论和输出格式对应的工具。

必须区分“12×9 个方格”和“12×9 个内角点”：如果前者成立，内角点通常是 11×8；本对话没有充分记录当时最终命令，不能反推使用了哪一个 `--size`。论文应重新核对标定板和原始标定输入，而不是只引用口头板尺寸。

### P02：腕部标定结果与去畸变像素坐标

用户提供的针孔标定结果，分辨率为 1280×720：

```text
K = [[683.0351877157348, 0, 629.9780030679196],
     [0, 689.4064870396259, 418.9316595398111],
     [0, 0, 1]]
D = [-0.28024828685428893, 0.05953061708134112,
     -0.0033341681831325514, 0.0022132051564490575, 0]
R = I
P = [[468.222331813079, 0, 637.4404354643108, 0],
     [0, 626.4484097000374, 428.2366255473854, 0],
     [0, 0, 1, 0]]
```

用户要求把 `/tmp/calibrationdata.tar.gz` 保存到抓取项目；当前项目中存在 `calibrationdata.tar.gz`。V3 文档规定以 `K,D,I,K` 建立去畸变映射，保持原尺寸和 K，不裁剪，命名为 `undistorted_K`。因此控制像素不能混用原始畸变图或 P 所定义的新投影图。

只有这组内参与畸变系数，不能宣称完整手眼标定已经完成；内参标定也不是腕部相机到工具的外参标定。

### P03：第七轴、法兰、工具 TCP 与指尖不应混为一谈

用户询问 URDF 右手法兰长度、第七轴和末端坐标系，希望三维可视化。已有结果目录 `right_wrist_frames_20261010`。

整理时核对的 URDF 中：`arm_J8_r` 是 `arm_L7_r → arm_end_effector_r` 的零平移、零旋转固定连接；夹爪基座连接另有 `xyz=[0,0,-0.005] m` 及旋转。这个 5 mm 是该固定连接的坐标偏移，不能直接当作整块法兰的物理长度。抓取参数中的 50 mm 指尖偏移也属于另一层几何量。

论文必须明确 TCP 指的是哪个 link、哪种安装模型；没有重新测量的机械尺寸不要凭日志猜测。

### P04：右臂三维工作空间还需限制抓取方向

先可视化普通右臂可达点，再按用户要求限制水平向前抓取。保存报告使用局部接近轴 `[0,0,-1]` 对齐基座 `[1,0,0]`，roll 自由；采样近端关节并求腕部姿态，再用原 URDF FK 验证。

`forward_stats.json` 记录 300972 个样本，坐标系为 SJ4Z，与 `arm_base_link_r` 重合。该可视化没有进行自碰撞、环境碰撞、路径可行性和指尖 TCP 偏移检查。因此它是姿态约束下的运动学采样空间，不是保证可安全执行的自由空间。

### P05：将空间叠加到头部图像，必须带入外参和坐标变换

从三维点云转成头部视角 AR，再按当前手高度切平面。用户特别追问是否考虑头部手眼标定。

保存的投影报告明确：使用现有头部外参，工作空间 SJ4Z 到相机外参基准 `dummy_world` 还含 `[0,0,342] mm` 平移；当时没有重新验证实际配准。报告中的像素叠加不是重新标定的证据。

### P06：静态快照、高度不更新与画面停滞

用户多次反馈移动手后平面不动、图像静止。问题要分层检查：页面是否只是静态结果、服务是否采到新图、是否订阅实时机器人状态、位姿是否新鲜、渲染缓存是否更新。

策略是将“当前手 TCP 的基座 Z”与头部图像/深度持续更新，显示最近有效结果和状态。不能把最初保存的平面当成当前高度，也不能把浏览器缓存误认为相机不动。

### P07：闪烁、深度抖动、断连后不能恢复

用户要求没有新数据时持续显示旧图，断开连接后继续监听并能恢复。后来取消独立闪烁的深度可视化，但仍要求深度参与明暗表达。

可视化方向演进：轮廓金色高亮 → 取消轮廓 → 类似水面的可达平面 → 面上保留原色、面下压暗 → 金色更明显。深度噪声、无效像素、位姿抖动、帧切换均可能使分类边界闪烁，不能仅凭肉眼认定是机械臂在抖。

显示层保留旧图是合理的，但控制层不能用旧帧继续运动。AR 状态显示与视觉伺服的时效要求不同。

### P08：AR 与抓取程序争用头部相机

用户要求头部图像“一分为二”，例如 ROS 形式。实际项目形成共享 RGB-D 源和多个客户端：硬件由单个采集源持有，AR 与抓取分别消费，避免两个进程抢设备。

V3.3 又在协议中同时提供原始分辨率和旧标定尺寸图像，保留兼容性。不能将“ROS 风格多订阅”的需求写成已经部署 ROS 话题，具体实现应以 `head_rgbd/` 为准。

## 4. 目标定义与头腕匹配研究

### P09：最终示教图与观测起点混淆

若把退回后的观测图误当目标图，伺服可能在起点宣布完成。用户明确了最终图和之后退回的位置。

记录文件：`v3_reference_current_20261009.png` 为最终参考，`v3_observation_before_stage2_20261009.png` 为观测图。早期四点目标绑定图像、相机标定指纹和固定书脊纹理位置。

两张实拍图的离线匹配记录为 12/16 内点、约 0.53 px 重投影 RMS，当前区域面积约为最终图的 0.0265 倍。它说明匹配可拟合，不说明机器人已到达，更不是 0.53 px 抓取精度。

### P10：为什么需要头腕匹配，为什么后来取消

最初是为了保证头部选的书、腕部跟踪的书和最终示教的书是同一本。用户一度明确要求验证身份一致。

随后发现：小头部书脊、明显视角变化、低纹理和近距离遮挡导致身份交接成本高。用户最终决定直接使用粗对齐后腕部中央书，接受同一目标假设。

这是任务约束的调整，不是匹配算法取得了普适成功，也不是头腕身份问题天然不存在。

### P11：不同颜色、不同书不能复用旧纹理目标

颜色变化本身并非唯一问题，书脊纹理身份也变化。原书最终图的四个物理点在新书上未必存在。解决方向由“复现同一图像”改为“当前书的几何中线对准＋实测深度终点”。

这种转向减少对特定书的依赖，但仍依赖当前可见书脊可被可靠识别。

### P12：头部特征点过少阻塞匹配入口

典型错误：`Selected book has too little visible texture`。一次现场输入为 `features=9/16`、`mask_bbox_px=23x92`，另有更窄的 10×75 px 区域。

早期程序在真正头腕匹配前就被 SIFT 初始化门槛拒绝。策略包括保存原图/掩码、区分头部身份验证与腕部跟踪初始化、增加 ROI 匹配和更换特征后端，而不是把所有失败统称“找不到书”。

### P13：XFeat 比较没有证明跨视角问题已解决

比较当前 SIFT、ROI SIFT、XFeat sparse/semi-dense 和相关匹配组合。保存了模型权重哈希、代码 commit、输入哈希及离线报告。

典型反例：某 XFeat 组合虽有 20 对候选、5 个内点、RMS≈0.88 px，但内点率仅 0.25，控制点支持/空间覆盖/投影尺度不合格。不能只看连线“像对了”或重投影误差小就放行控制。

### P14：SuperPoint+LightGlue 改善部分腕部匹配，但低分辨率头腕仍困难

保存的比较摘要：5 个真实头部输入、4 种变体，共 20 次头腕几何检查，0 次通过；候选身份试验 72 次，0 次纹理准入通过。某最终腕部图到当前图组合得到 29/41 内点、RMS≈1.07 px。

这些是小规模、非完整标注的离线样本，不能作为模型总体准确率；也说明腕部间匹配改善不等于头腕匹配解决。

### P15：提高头部分辨率与放宽“单帧身份成功”标准

用 1280×800 原始图与同一图降采样到 848×530 对照，重新采集目标同时出现在头部和腕部的观测。

记录中，浅色书最好内点数从 0 到 5，红色书从 0 到 6；深色书并非总改善。放宽后的单帧候选身份规则：至少 6 内点、内点率≥0.65、RMS≤1.5 px 等，出现 1 次候选通过；完整几何控制检查仍为 0。

应明确区分“允许视为单帧候选匹配成功”和“单应性足以传递控制点并运动”。手工候选 ROI 也不能作为自动目标身份的真值。

### P16：在线仍走旧入口，离线改进未实际接入

用户看到高分辨率匹配效果好，但运行时又报旧 `features=9/16`。暴露出算法演示、在线入口、共享图像分辨率和实际启动进程之间的差异。

策略：启动时打印后端/分辨率/模式，显式选择配置，重启加载 Python 修改；用运行目录保存输入和方法名。按回车开始新一轮通常不会重新加载 Python 源码。

## 5. 从点目标到中线目标的感知算法迭代

### P17：用距离定义前伸终点，而不是跨书复用最终图

采用本轮 V1.3 计算：

```text
x_goal = x_book_surface + grasp_insertion - fingertip_x_offset
```

偏移须按工具姿态投影到基座 X。常见配置为伸入 100 mm、指尖名义偏移 50 mm。头部深度经标定变换到基座坐标后才参与计算，不能把相机 Z 直接当基座 X。

这是距离驱动的终止条件，不是接触检测，也不保证视觉无误差或真正夹住书。

### P18：CoTracker 跟踪点方案及其成本

讨论过 Track Anything，实际尝试 CoTracker3：在当前书中部选择约 8 点，至少 6 点可见；短窗口推理，Y/Z 对齐后前伸。

遇到 `CoTracker point geometry inconsistent`：剩余点的运动不再支持同一个几何模型，可能涉及误跟踪、跨表面、遮挡等，不能仅凭该错误唯一确定是哪一种。点可见不等于点几何可信。

后续为了减少计算量和不必要的 Z 调整，转向中线模式。

### P19：不要把书的上下中心作为必要目标

用户明确只需横向对准书脊中央列，书不完整入镜也应可用。因此不再强求二维中心点的 v 坐标居中，固定基座 Z；中线横向位置在图像中心行求交，避免可见高度变化拖动目标。

这一步减少任务自由度，也减少对完整分割和上下遮挡的依赖。

### P20：倾斜书需要控制中线方向

仅 Y 平移不能纠正倾斜。引入工具轴旋转，使中线穿过中央并趋于竖直。

当前等效图像误差为 `[u_centerline - u_image_center, theta_centerline]`；通过 Y 和工具轴旋转的小探测，估计 2×2 图像 Jacobian。探测使用实测位移，不以指令位移假定机械臂完美执行。

### P21：中线不是特征点重心；斜视封面会造成偏置

用户发现书斜着时把封面点也算进去，中线偏向右侧。原因是整书掩码包含可见封面，用整书轮廓或混合点集定义书脊中心不合理。

策略：先定位整书，再明确选择 `book spine` 表面；中线由书脊两侧几何得到，内部纹理点只传递中线。限制采点在每行中间 60%，并为 LK 窗口留出边界余量。

一张斜书回放中，整书中心列 569.95 px，书脊中心列 504.96 px，相差约 65 px；这证明该帧的目标定义存在显著偏差，不是机器人控制误差造成的全部偏移。

### P22：纯边界跟踪与特征点跟踪的取舍

用户先提出不计算特征点，直接追边界和中线；后又要求恢复特征点，在点数不足时转为直接距离前伸。

最终形成：书脊语义/边界负责定义中线，Shi–Tomasi 选点、LK 前后向光流和 RANSAC 负责帧间传递。当前最多初始化 80 点，低于 6 个可靠点触发特定的丢点分支。此时已不是 CoTracker。

### P23：两种失败必须分开

- **点逐渐丢失**：可靠点少于 6。按用户要求先保持并确认，固定 Y/完整姿态和原参考 Z，按原 X 终点继续。结果须标记 `visual_alignment_verified=false`。
- **几何缺乏共识**：还有点，但不能支持一致中线，例如 RANSAC 内点占比低于 60%。原先直接停止；最新改为停稳后请求 GPT 恢复。

不能把“点多但互相矛盾”当成正常遮挡然后盲目前伸，也不能把 GPT 恢复验证时的丢点误当成旧目标自然丢点。

### P24：初始化没检测到书，不能直接进入距离前伸

`No book detected in the wrist image` 发生在目标尚未锁定时；与后续可信目标的点逐渐丢失不同。先改进 book/spine 检测召回、掩码几何和备用识别，而非跳过初始化。

## 6. 边界、透视与 GPT 感知备用的演进

### P25：左右边“平行 5°”门槛误拒透视

书脊在透视下两侧可收窄或展开，不应仅用方向差≤5°。改为检查整个共同观测区间：不交叉、宽度为正、宽度变化平滑、拟合残差合理、真实像素边缘连续。

一张失败帧回放中，两边方向差 5.21°，宽度 117.47→79.54 px，比值 1.477，边缘支持率约 98.56%/100%；按透视一致性检查可用。该结果不是“把角度阈值无限调大”。

### P26：短线段、文字内部笔画与外边界混淆

后续 `No supported perspective-consistent wrist boundary pair` 并非继续放宽角度就能解决。V3.4 尝试 LSD 短边段连接、Huber 外边界拟合，再回查整个区间的边缘连续性。

增加 Lab 色度支持，处理等亮度、不同颜色的表面；在边界两侧不同距离检查颜色阶跃方向，抑制书脊文字的细笔画。长缺口不能仅凭线段连接补成可靠边。

两张保存帧边界备用中位耗时约 0.15–0.16 s，均可初始化 80 点。耗时不含 SAM3、采集和运动，不能换算成完整闭环速度。

### P27：多个候选导致歧义，重复拟合不能当成多本书

错误：`Wrist boundary selection ambiguous between multiple pairs`。

先合并高度重叠、边界偏差小、区域 IoU≥90% 的重复拟合；组内所有成员都须一致，防止链式合并不同书。真正相邻书、共享边界条带和书缝歧义仍拒绝。

一例重复候选合并后 IoU=98.19%，得到唯一中心列 744.50 px；但同一图人工平移 12 px 后原有检查仍可能无候选，说明鲁棒性没有被这一修复完全解决。

### P28：掩码全长宽度变化大，局部可见表面仍可能有效

对平稳透视收窄，尝试去除上下端部各 5%–20%，保留跨中心行、至少一定长度的内部支持区间；内侧边界必须连续，不能把内部台阶或断裂当作透视。

回放例：使用第 108–608 行，中线 u≈690.5 px，得到可初始化区域。没有凭空补画被遮挡的书脊。

### P29：SAM3 无可靠书脊，头部接 GPT+SAM2

用户提出 SAM3 未检出时让 GPT-6 选择书脊。早期实现为 GPT 输出书脊/整书四边形，SAM2 依据框和内部点细化，再过几何与深度检查。

配置使用现有模型 `gpt-6-astra`、60 s 超时、最低模型自报置信度 0.7。这里的置信度不是经过统计校准的识别成功概率。密钥文件只记录路径，不在本文复制密钥内容。

### P30：GPT+SAM2 的结果不一致

出现 `SAM2 disagrees with GPT book/spine surface`。SAM2 细化可能扩大到封面或其他表面，增加一个拒绝环节。

用户明确要求 GPT 能圈定就不必用 SAM。最终头部和腕部备用都直接将 GPT 四边形栅格化为掩码，不再调用 SAM2；书本专用感知还跳过不需要的 SAM2 embedding。此区域是模型提议的多边形，不是像素级人工真值。

### P31：GPT 分割成功，但深度一致性失败

典型错误：`Spine center depth is mixed with background`，或 `No sufficiently long continuous stable-depth spine region`。语义区域对了不保证其深度没有背景、孔洞和混合像素。

用户要求 GPT 路径不做原深度一致性拒绝。当前策略是仅对 GPT 候选跳过中心深度离散度拒绝及稳定区域回退，仍取有效实测深度中位数；整书有效深度仍用于 X 终点，无有效深度仍不能继续。SAM3 路径保留原检查。

一次保存帧中心深度 P10≈785.24 mm、P90≈890.4 mm，差约 105 mm，超过旧 100 mm 门槛；离线新策略能提取中心中位深度 833.9 mm。**能提取不意味着混合深度被证明准确**。这是明确的任务策略放宽，论文需报告可能影响终点误差的风险。

### P32：三维倾角不可靠，J7 调整应跳过

错误：`Reliable 3D spine tilt required for J7 alignment`。用户要求失败则跳过。

当前无可靠三维倾角时跳过头部 J7 预旋转，保持姿态继续 Y 对齐，后续腕部视觉再对准。若已经发送的 J7 动作执行失败，仍不能假装完成。需区分“没有可用预旋转估计”和“实际运动失败”。

### P33：每轮首次感知必须无论成败都可见

此前只有报错，难以判断是检测错、几何误拒还是书不在视野。用户要求首次感知一律可视化。

当前输出 `first_detection.html`，显示原图、SAM3 掩码、GPT 提议、选择和中线、失败原因；固定查看入口 `RobotRAM/output/wrist_first_detection/index.html`。中间伺服快照仍每 200 帧一次，避免高频写盘拖慢控制。

### P34：连续跟踪中线无法推算时让 GPT 恢复（最新）

触发场景：完成探测后，`Centerline geometry lacks consensus`、拟合失败或中线几何跳变。最新流程：

1. 确认机械臂有限位置保持，不再继续更新前伸目标。
2. 保留原始高度和 X 终点，采集停稳后的新腕部图。
3. GPT 重新圈定当前书脊，重建特征跟踪器。
4. GPT 返回后再次采集新图，检查跟踪、图像时效、位姿配对和目标连续性。
5. 通过才恢复；API 期间位姿漂移、超时、区域无效或新图失败仍停止。

每轮最多两次。恢复不重置路径和总时间预算；保留图像尺度衔接。若在 Jacobian 探测中换了跟踪器，丢弃跨越切换的探测差分，重新完成两轴探测。

最新离线验证还修复了两个细节：停稳参考必须复制，避免共享反馈对象更新掩盖漂移；恢复验证时点不足必须转为普通失败，不能触发“直接前伸”。记录在 `gpt_recovery_01/02`，包含失败帧、GPT 输入、验证帧、掩码和 JSON。

本次 66 项离线测试和配置检查通过，未进行新的实机抓取验证。GPT 恢复有秒级延迟，定位为停稳后的事件恢复，不是 10 Hz 外环里的逐帧模块。

## 7. 分步运动、时间同步与预算问题

### P35：粗前伸返回完成，但一次反馈未到位

错误：`First-stage waypoint was not reached`。控制器的 finished 状态不等于某次读取到的 TCP 已稳定达到目标。

策略：粗前伸单独用 8 mm 标准，等待新鲜反馈和连续稳定样本，打印 target/actual/delta、姿态误差和稳定计数。后续现场有 0.567 mm、0.430 mm、0.617 mm 等通过记录，证明该检查链至少在这些运行中工作。

### P36：2 mm 小步被原规划器的目标去重逻辑吞掉

现场目标 Y 改变约 2 mm，实际仍在原处，却很快收到完成状态。历史原动作的约 5 mm 目标变化识别可能把微步当作重复目标。

修复方向：视觉动作专用目标变化判断、专用到位标准和新命令身份。不能只把客户端到位阈值放到大于整步位移，否则“不动”也可能被接受。

### P37：小步与到位容差不匹配、两层标准不一致

早期视觉步长 2 mm、到位阈值 1 mm；后用户要求 2 mm、再改为 3 mm。容差影响最终确认，但不能同时当作忽略新目标的阈值。

客户端与执行后端应分别明确定义：命令是否新、实际是否到位、运行中是否偏离平面、X 是否达到终点。当前 V3.4 位置到位 3 mm，不代表 Z 可任意偏移或 X 终点也放宽到 3 mm。

### P38：结束后等“最多 10 秒”不等于每步固定等 10 秒

多次日志先打印“继续等待最多 10.0s”，随后约 0.2 s 稳定窗口就通过。慢的来源可能是规划、插值、执行、采集和确认之和，不能把该提示文字直接当作实际耗时。

可靠确认使用不同时间戳的反馈，重复读同一缓存不能累计 `stable_samples=3/3`。

### P39：第二段剩余距离超过预算

例：实际 X≈519 mm，目标 X≈731 mm，剩余约 212 mm，超过原第二段允许行程，报 `endpoint exceeds remaining CoTracker travel budget`。

用户要求第二段预算覆盖距离，并同步增加总路径预算。这里需要同时计入粗前伸已完成量、第二段距离、探测和纠偏；单改一个字段不保证可完成。

### P40：X 区间误判与反馈微小漂移

仅 Y 探测或返回时，实际 X 有亚毫米变化；若严格用旧起点或旧指令 X，可能触发 `Measured/commanded X outside approach interval`。

策略是基于最新实测位姿构造保持目标，用明确容差处理正常跟踪误差，避免探测返回旧 X 造成不必要回退。不能因此放开终点超越。

### P41：Y/Z 20 mm 是软件预算，不是物理极限

`Y/Z travel bound exceeded` 的原因可能是下一步纠偏目标超过相对起点的 20 mm 范围，并非机械臂不可达。用户要求不限制或放宽。

后续首先缩减任务维度、取消不必要 Z 对齐，再区分横向预算、总路径预算和物理工作空间。即便取消某个单步上限，仍保留深度终点、总路程、时效、碰撞和状态限制。

### P42：重复 JSON 键和配置值范围

曾出现同一段 JSON 同时有 `max_step_mm:20.0` 和 `max_step_mm:5.0`，以及 `Invalid CoTracker setting: max_step_mm`。普通 JSON 解析常以后一个键覆盖前一个，但这种配置不能用于可重复实验。

应保留唯一字段，检查入口实际读取哪份配置；修改参数后执行 `--check-config`。连续版中的 stream gain/lookahead 与旧 column gain/max_step 并非同一个控制量。

### P43：每帧起子进程采图，0.5 秒超时

错误来自 `--capture-worker ... frame.npz timed out after 0.5 seconds`，包括进程启动、设备打开、预热丢帧等成本。

改为独立常驻采集进程，持续读取，按请求提供新帧；后续减少持续采集中的重复预热丢帧。保留请求编号、时间戳、格式和新鲜度检查，不能为了速度使用运动前缓存。

### P44：运动期间，图像必须与对应时刻位姿配对

旧逻辑可能把采集前位姿或处理完成后的位姿与图像配成一组；运动越快，错误越明显。

策略是缓存带时间戳反馈，寻找图像时刻两侧位姿并插值；区分等待图像期间真实运动和配对的不确定性。相机时间是主机读取时间，UDP 时间是主机接收/记录时间，不是已验证的硬件曝光同步。

### P45：PoseNotBracketed 与配对支撑过宽

典型错误：无前后反馈包；或支撑运动达 6.271 mm、角度 0.193°、间隔 0.0214 s，无法满足当时约束。

正确方向是恢复反馈、重新采集新图、检查时间基准和插值误差，而非只把 3 mm 限制放大。短暂失败暂停目标更新；持续超时才退出。恢复期间最后有限目标可能仍在执行，并非瞬时刹停。

### P46：配对恢复超时可能源于规划器已经退出

用户贴出 `pose pairing recovery timed out` 后，进一步提供规划器异常，才定位到状态生产端退出。感知端等待不到反馈是下游症状，不等于相机算法坏了。

诊断应同时记录进程存活、反馈最新时间、协议状态和原始 Traceback，避免循环调图像阈值。

## 8. 连续运动、规划器和协议问题

### P47：每个视觉步完整规划并停稳，速度受固定开销支配

停走模式每步要经历目标发送、MotionGen、轨迹执行、稳定确认、采集和计算。把 2 mm 改成 5 mm 有限改善，但没有消除固定开销。

V3.1 首先允许运动中更新目标；后明确只在视觉阶段使用差分伺服。探测和最终确认仍阻塞，不能将“连续”理解成完全不检查反馈。

### P48：增大 gain 和步长不等于提高运动带宽

用户先要求 gain>1、步长>1 cm，再尝试 gain=5、步长=100 mm、取消单步上限。

较大的远期目标受执行速度、滤波和跟踪滞后限制；较大增益反而可能使 Y/旋转来回修正、增加路径。解除底层速度瓶颈后，gain=5 的振荡更加明显。最终 V3.4 连续视觉 gain 降至 0.35，并以有限前伸领先距离平滑推进。

### P49：时间缩放 1 与 0.9 的含义

在历史 MotionGen 视觉路径中，记录显示 time_scale=0.9 时 `waypoints_dt≈0.2222s`，而 time_scale=1 时约 0.2s。可见该实现中 0.9 对应更长时间，并非“缩短到 90%”。

必须看库和实现的实际语义，不能把“缩放”名称直接理解为时间乘数。当前 CPU 直接视觉伺服不使用这条 MotionGen time_dilation 参数；普通动作另有参数。

### P50：规划轨迹 Z 合格，不代表实际执行高度合格

现场长前伸目标约 168 mm，规划最大 Z 偏差 10.720 mm 被拒；缩半后预测 2.747 mm 通过，但后续实际高度仍超过原平面 4 mm，例如从 -10.951 mm 下沉到 -15.522 mm。

日志还显示远处 X 目标与接近旧 X 的纠偏目标交替。解释方向是旧图目标、重规划起点、轨迹切换、面板插值和实际跟踪误差共同作用；仅凭一条 Z 超限不能确定单一根因。

策略：保证前伸/纠偏切换不倒回旧 X；统一目标与执行起点；校验面板实际插值路径；为跟踪误差预留余量；独立于规划线程监测实测高度。

### P51：高度超限时缩短前伸重规划，而不是扩大安全边界

历史 V3.1 对超限目标按 1、1/2、1/4 等比例重试；保留完整请求终点，但执行当前可接受段。后来将预测高度范围收至 2 mm，为总 4 mm 客户端范围预留 2 mm 跟踪余量。

仅检查路点终点的 Z 不够，必须检查轨迹中间值。缩段也无法自动解决不同轨迹之间的接续。

### P52：面板路径验证耗时导致起点过期，反复重规划

现场多次出现 `panel path validation start expired`，连续重试至第 4 次才 segment accepted。客户端 meanwhile 报 ACK timeout。

这揭示“验证越多越安全”并非无条件成立：验证期间机器人仍运动，起点会失效。需要验证实际接续、合理划分保持状态和规划状态，并绑定已下发请求，而不是无限重试陈旧起点或单纯增大 ACK 超时。

### P53：ACK 超时与状态=4、target_matches=False

状态显示某动作完成，不代表当前请求已被接收。旧目标、缩段目标、未发送的规划结果和新请求之间身份不一致，都可能造成客户端等不到正确 ACK。

策略：命令 nonce/序号和目标副本绑定；只确认实际下发的请求；失败状态带具体原因。`PLANNING_FAILED` 在统一协议里只是状态枚举，不保证失败一定来自 CuRobo。

### P54：共享 GPU FK 缓冲区尺寸冲突

错误：`get_link_poses` 期待 `[1,3]`，实际得到 `[4,3]`。发生在状态发送线程计算 FK 的路径。

工程问题是单状态 FK 与批量规划/校验复用模型或缓冲区时的并发/批尺寸管理。修复方向为隔离反馈 FK 模型、受控访问共享 GPU 数据并报告线程异常，避免状态线程静默死亡。不是视觉特征点导致的错误。

### P55：NumPy 零维数组与 list 类型错误

两条明确软件缺陷：

- `arm_waypoint_dt=array(0.2,dtype=float32)` 传给期望标量或可迭代格式的协议函数，报 `TypeError: iteration over a 0-d array`。应在协议边界规范成正确标量类型。
- `gripper_joint_position` 有时是 list，代码直接 `.tolist()`，报 AttributeError。应统一类型再转换，而不是假定所有输入都是 NumPy 数组。

这些问题说明模拟规划通过还不够，需要覆盖真实命令打包和两种输入类型。用户对频繁出现这些基础缺陷表达了明确不满，应保留为工程复盘教训。

### P56：只替换视觉阶段的执行后端

当前视觉命令 `book_v3_xyz_servo`、`book_v3_1_stream` 用 CPU FK 和数值机械臂 Jacobian，将 TCP 误差映射为关节增量，以 RAW 关节位置下发。

普通复位、粗定位、抓取后动作仍用 CuRobo；一个进程统一持有面板 UDP，避免两个控制器竞争。启动日志 `MotionGen bypassed` 是判断视觉后端的证据，不能只根据文件名判断。

### P57：直接伺服仍受预测高度保护约束

错误：`Direct servo predicted Z path outside tracking reserve`。其含义是候选关节动作的预测 TCP 路径超限，不是 MotionGen 规划失败。

策略包括缩减“实际反馈到候选命令”的完整领先量、清除被拒绝增量的积分、必要时优先恢复 Z，并保持原参考高度。无可行步时有限等待、持续失败停止，不无条件取消 Z 检查。

### P58：50 Hz 后端仍很慢——RAW 目标斜坡与低通滤波

检查到底层 RAW 分支仍有默认 5 秒目标追赶斜坡和 2 Hz 低通滤波。只提高上层发送频率不能消除它们。

仅视觉命令设目标时间为 0、速度比例 0.3；普通动作恢复其参数。目标时间 0 不是瞬时跳到位，仍有滤波和关节速度/加速度/领先量限制。

历史离线真实插值器对照中，同一 0.2 rad 目标、3 s 内位移由约 0.0141 rad 到 0.2002 rad；这是该模型/滤波测试，不是实机速度提升倍数。

### P59：振荡、累计路径耗尽和无实测进展

现场出现 `V3.1 path budget`、`no measured progress`、丢点前后 Y 来回运动。大增益、有限执行带宽、恢复反复切换、锁定参考不一致都是需分开观察的因素。

修正包括降低视觉增益、限制前伸领先量、恢复后渐增、统一实际锁定参考、保留累计路径诊断。不能靠把总预算无限放大掩盖振荡。

### P60：丢点切换后 pose drift

保持动作有容差，保持后的实测 Y/Z/角度不一定与保持前一致。如果发命令用一份参考、漂移检查用另一份参考，就会反复恢复甚至误停。

V3.2 一次锁定 Y 和完整姿态，Z 始终使用原平面；检查完整旋转差而非单 roll。短暂越软阈值时暂停增加前伸，连续稳定恢复后再推进；越硬限或持续恢复失败则退出。

### P61：400 mm 预算边界与真实不足需分别处理

现场打印 `used_mm=370.1, requested_mm=29.9, limit_mm=400.0` 看似恰好相等，可能隐藏舍入误差。修复只容忍 64 ULP 的浮点误差，并打印更高精度，不用毫米级容差放宽预算。

另一轮真实记录中，距离终点仍约 44.19 mm，预算只剩约 29.9 mm，且出现 13 次姿态恢复、11 次高度恢复；这是真实路径不足，数值修复不能解决。V3.4 加入恢复渐进前伸和分项路程日志，再评估预算。

## 9. 通信、硬件与普通动作故障

### P62：No robot state received 不是未识别到书

识别前 first_reset 需要机器人状态；没有状态时复位失败，后续日志又说找不到 object_0。最上游是反馈/进程/UDP 链路问题，不能被“未找到书”的下游描述误导。

后来确实出现规划器异常退出，使状态发送停止。应先恢复状态生产和通信，再谈视觉。

### P63：规划生成但机械臂完全没动——上层 watchdog 锁定

用户提供 `[REMOTE WATCHDOG] Planner command stream lost; holding measured joints. Press Start to resume.`，并确认完全没动。

原因链是耗时规划与指令发送耦合，通信断流触发保护；反复 Start 只解除当前锁定。策略是独立 20 Hz 发布线程，规划期间保持一个固定实测关节目标，不发送尚未规划的远期目标；反馈/生产者 lease 和规划 deadline 仍有限，原 0.5 s watchdog 保留。

后续还处理保持起点与实际规划起点变化：丢弃过期轨迹、保持并等待稳定、从新鲜反馈重规划，而不是为不断“保活”发布过期运动。

### P64：更换右夹爪电机 ID 与串口打开失败

用户先说手部相机电机，随后明确是右手夹爪，将 ID 2 改 1；之后报 `tcgetattr: Bad file descriptor`、`Failed to open gripper1`，再要求改回 2。

电机 ID 与串口文件描述符是不同层级。该错误首先说明串口打开或句柄无效；不能只凭它确定是 ID 错误，仍需检查设备路径、占用、权限和配置。最终需求是恢复 ID=2，论文不应把这次硬件配置故障归入视觉控制失败。

### P65：INVALID_START_STATE_SELF_COLLISION / GRAPH_FAIL

复位时当前状态或起终点被碰撞模型判定不可行。可能涉及真实姿态、自碰撞模型、初始关节反馈或目标姿态；仅这两条状态不足以判定是哪两个 link。

应核对实测关节、模型和碰撞对，再可视化；不能以关闭碰撞检查作为默认解决。本文未见足够证据证明这些特定现场失败的唯一根因和最终实机消除结果。

### P66：抬升后增加 40 mm 前伸，失败则从实际位置下降

用户要求抓取抬升后先向前 4 cm 再竖直放下；随后明确前伸失败就按原方式下降。

当前顺序：抬升 200 mm → 停顿 3 s（沿用原姿态处理）→ 尝试 X 前伸 40 mm → 从最新实际位姿固定 X/Y 分段下降 150 mm、每段≤50 mm。若前伸返回失败，读取实际位置再下降；不能假定 40 mm 全部完成。无有效位姿、人工中断或下降失败不能继续假成功松爪。

离线测试覆盖成功前伸、只完成部分前伸、失败后按实际位置下降和无反馈停止。

## 10. 当前算法表达（供论文整理，非完整控制律证明）

### 10.1 几何目标

设可见书脊左右边界为 `u_L(v), u_R(v)`，局部中线为：

```text
u_C(v) = (u_L(v) + u_R(v)) / 2
v_0 = (H - 1) / 2
s = [u_C(v_0), theta_C]
s_goal = [(W - 1) / 2, 0]
e = s - s_goal
```

区域不完整时只用共同可见且可靠的区间，不外推不可见顶部/底部。局部跟踪通过几何变换传递这条线，不把纹理点质心当作中线。

### 10.2 两层 Jacobian 的区别

图像外环估计：

```text
delta_s ≈ J_image * [delta_Y_mm, delta_roll_deg]^T
```

通过实际探测位姿和对应图像响应拟合。阻尼求解的概念形式为：

```text
delta_a = -lambda * (J_image^T J_image + mu^2 I)^(-1) J_image^T e
```

实际实现还包括误差归一化、条件检查、步幅/领先量限制、尺度补偿、前伸准入和状态恢复，不能只用这行公式代表完整代码。 整理时的连续实现使用按容差归一化的 `A`、误差死区处理后的 `b`，求解 `correction = -gain * solve(A.T @ A + 0.02 * I, A.T @ b)`；不要把概念公式中的 `mu` 直接写成当前 JSON 中一个并不存在的可调字段。

执行内层另用机器人运动学 Jacobian 将 TCP 误差转换成关节命令。**图像 Jacobian 与机械臂 Jacobian 不是一个矩阵。** 当前是在未知/未完整使用腕部手眼变换条件下，从基座动作实测估计等效图像响应，并不意味着头部 RGB-D 外参可以省略。

### 10.3 X、Y、Z、旋转的分工

- X：到本轮真实深度终点；对准差、恢复中或临近终点时收短目标。
- Y：使书脊中线横向居中。
- Z：保持本轮参考高度，不追书脊上下中心。
- 工具轴旋转：使中线方向对准目标竖线；不是任意调整所有姿态轴。
- 丢点距离模式：停止图像纠偏，保持已锁定 Y/姿态和原 Z，继续有限距离；不标记视觉验证成功。

### 10.4 多频率与延迟

当前配置的 10 Hz 是视觉目标更新上限，50 Hz 是直接关节伺服目标周期，20 Hz 是面板独立通信发布策略中的频率。实际相机、模型、CPU 调度、通信与执行频率需要实测，不能互相代替。

GPT 是秒级停稳恢复。规划时间缩放、视觉增益、TCP 速度上限、RAW 速度比例、低通滤波频率也都是不同参数。

## 12. 可用于论文的结论与不能声称的结论

### 已有依据的经验

1. 抓取特征应由任务决定：书脊中线比整书质心更符合侧向夹持需求；斜视封面混入会造成明显偏差。
2. 跨视角身份匹配、局部连续跟踪、最终几何对准是三个不同问题，不能用同一“匹配成功”指标概括。
3. 软件完成状态与实机到位需要分别验证；目标去重阈值与到位容差必须适应小步控制。
4. 连续控制依赖时间同步、命令身份、轨迹接续和底层带宽；单纯提高 gain/步长可能恶化振荡。
5. 目标参考必须跨模式保持一致，特别是丢点和高度恢复不能偷偷重置平面。
6. 透视书脊不一定平行；边界连续性与宽度变化比单个角度硬阈值更合理。
7. 低频语义恢复与高频局部控制可以分层，但必须处理 API 延迟和恢复验证，不能直接控制于旧图。

### 尚不能据此宣称

- 对任意书本、视角、光照均可靠；或已完成大规模抓取成功率验证。
- XFeat/SuperPoint/GPT 谁总体最优；现有比较规模、输入与任务条件不足以支持这种结论。
- 取消头腕匹配后仍有自动身份一致性保证。
- 距离模式完成等同于视觉收敛、接触成功或夹持成功。
- 50 Hz 配置等于硬实时；10 Hz 配置等于实际端到端视觉频率。
- 离线 RMS、FK 误差、测试数或模拟高度偏差等同于实机抓取精度。
- AR 可达区域等同于无碰撞、可规划或可抓取区域。
- GPT 直接四边形是精确像素分割；跳过深度一致性检查等于深度可靠。
- 本次最新 GPT 恢复已在实机连续运行中成功。

## 13. 建议补做的论文实验

### 13.1 对照与消融

在尽可能相同的初始位姿、书本、光照和相机条件下，比较：V1.3 无视觉、停走视觉、连续 MotionGen、CPU 直接伺服；整书质心与书脊中线；固定图像示教与几何目标；低分辨率与原始分辨率；SAM3、SAM3+边界、SAM3+GPT；有/无 GPT 跟踪恢复；高 gain 与当前 gain；有/无时间戳配对和状态恢复。

这些是待开展的实验，不应把历史逐次调参、不同场景运行直接当作公平对照。

### 13.2 指标

- 感知：书脊选择正确率、中线误差、倾角误差、误选封面/邻书率、初始化成功率、几何拒绝率、连续有效时长。
- 控制：首次对准耗时、总抓取耗时、实际目标更新率、P50/P95/P99 延迟、Y/roll 振荡幅度、Z 最大偏差、X 超调、累计路径、恢复次数。
- 系统：ACK/反馈断流、采集超时、规划失败、协议异常分别计数，不混进单一视觉失败率。
- 恢复：GPT 触发频率、响应时间、区域正确率、停稳恢复成功率、恢复后再次失败率、每次调用成本。
- 最终任务：真正夹住并抬起/放下的成功率，目标书身份正确率，以及人工介入次数。

## 18. 新增故障：粗前伸压满关节软限，局部探测失败（2026-10-12）

### P67：可达且终点无碰撞，不代表给后续视觉伺服留有余量

本轮 `v3_column_17ad5513ab9f4874b22e742b2c0cfe49` 粗前伸到位检查通过、80 个点初始化成功，但首次 Y +3 mm 探测被直接伺服后端以 `Direct servo joint limit` 拒绝，抓取端等待约 40 秒后报 `probe not confirmed`。前面的 stale-start plan 已重规划成功，是不同事件。

## 19. J7 可选预对齐的另一类不可用条件（2026-10-12）

### P68：三维拟合 valid 不等于 J7-only 对齐可行

生成子任务后报 `Spine is too parallel to the finger approach axis for J7-only alignment`，尚未进入 Y 粗对齐或前伸。当前函数将估计书脊方向投影到工具轴法平面，投影长度 <0.5 或非有限即拒绝。单独绕工具轴旋转不能改变书脊与该轴的夹角，因此这里没有可靠 J7-only 对齐解。

原跳过分支只识别 `spine_3d_status != valid`；此次拟合标成 valid 但投影不可用，落入异常中止，未覆盖此前用户“预估失败则跳过”的意图。当前保存记录的三维轴约 [-0.9787,0.1389,0.1510]、竖直倾角约 81.32°，应检查深度与所选区域，而不能断言实物书脊真的接近水平。该共享场景文件会覆盖，以上是本次读取的数值。

应区分可选预旋转的几何不可用与已经下发后的运动失败；前者可按任务约定跳过，后者不能假完成。此轮只完成原因核查和记录，未修改代码或实机验证。分类记录 Q-20261012-005。
